# 技能详解指南

面向使用者的通俗导读：17 个技能各自解决什么问题、什么时候用、会带你走什么流程、最后你能拿到什么。读完本文不需要再去读协议就能日常使用；协议原文以 `skills/<技能名>/SKILL.md` 为准（英文树 `skills-en/` 同构）。

安装见[安装指南](install.md)，方法论全貌见 [C1–C10 方法合同](harness-method-contract.md)。

## 为什么需要这套技能

现在的编码 agent 很聪明，但聪明不等于可靠。没有规矩的 agent 常见三种翻车：

1. **会忘**：会话一长或一断，前面聊定的方案、做过的验证全部蒸发，换个会话从头再来。
2. **会谎报完工**：「已完成 ✅」张口就来，但你一跑发现测试没过、文档没更新、验收根本没对过。
3. **会留垃圾**：干完活不收尾——过期文档、临时脚本、没人引用的计划文件越积越多，几个月后仓库自己都看不懂。

这套技能就是给 agent 立的工作规矩：**入口清楚（先聊清楚再动手）、状态落地（断了能续）、验证真实（完没完成看证据）、收尾干净（干完不留垃圾）**。每个技能只管一件事，按需触发，不是必须从头到尾走一遍的流水线。

## 先弄懂三个词

整套技能反复出现三个术语，用大白话先解释一次：

| 术语 | 大白话解释 |
| --- | --- |
| **Spec** | 一份需求说明书，写清「做什么、不做什么、做到什么程度算成功、怎么验证」。你批准它之后才动手写代码——避免 agent 理解错方向狂奔三条街。 |
| **恢复面** | 任务的存档系统。`work_index.md` 是任务清单（每行一个任务），`state.md` 是当前断点（干到哪、证据是什么、下一步是什么）。会话断了，新会话读这两份文件就能接着干，不用你复述。不是每个任务都需要——小任务零文件，任务确实要跨会话时 `plan` 会自动建。 |
| **fresh evidence** | 刚刚真实跑出来的验证结果（命令输出、测试结果），而不是「我记得之前跑过」。相关代码没变时旧证据可以复用；代码变了就必须重跑。完成声明只认这个。 |

## 车道技能：日常工作的主干道

### brainstorm —— 把模糊的想法聊清楚

**解决什么问题**：你想做个功能，但只说了半句话。直接让 agent 动手，它多半会按自己的脑补把方向做歪，返工比从头做还贵。

**你会怎么说**：「我想给项目加个评论功能，先别动手，帮我聊清楚」「这个需求有点模糊，先 grill 一遍」。

**它带你走什么流程**：

1. **拷问（frontier grill）**：把所有还没定的关键问题一次性编号列出来问你——每题附一个推荐答案，你只需要逐条确认或改答案，不用自己组织语言。问题覆盖目标、边界、技术取舍、成功标准、怎么验证。已经清楚的就不问，不会拿「业界惯例」替你做决定。
2. **写 Spec**：问题清零后，起草一份 Spec 给你过目。短需求走轻量版（Thin Spec），一轮问完，不搞成论文答辩。
3. **等批准**：你说了「批准」才交给 `plan`。沉默不算批准，它不会自作主张往下走。

**你会得到什么**：`docs/specs/日期--主题.md` 一份需求说明书，以及「方向没跑偏」的确定性。

**怎么配合**：批准后自然交给 `plan`；如果聊的过程中发现项目本身缺工作台（比如连个入口文件都没有），它会提示是否要 `harness-builder` 介入。

**小贴士**：需求其实已经想得很清楚、或者只是单行小修补，就跳过 brainstorm 直接干活——它自己也会这么建议。

> 协议原文：[`skills/brainstorm/SKILL.md`](../skills/brainstorm/SKILL.md)

### plan —— 把已定的目标排成可执行计划

**解决什么问题**：任务有多个步骤、步骤之间有依赖、或者一个会话干不完。没有计划，agent 容易做到一半忘了整体目标，或者把「每一步都过了」当成「整体能用」。

**你会怎么说**：「按这份 Spec 排个计划」「这个任务有点大，先规划一下再动手」。

**它带你走什么流程**：

1. 从你已有的材料（请求、批准的 Spec、issue）提炼目标、范围、验收标准——不会让你再写一套需求文档。
2. 写计划：目标、范围、可打勾的工作项、每项怎么验证、依赖关系，多阶段任务还会写**最终整体验收标准**（防止「每步都过但整体是散的」）。
3. 任务确实需要跨会话恢复、而项目还没有存档时，自动建**最小恢复面**（一个任务清单 + 一个断点文件，并在项目入口挂一行指针）——这是自动的，你不用预先决定。
4. 你只要计划：交付计划就停。你已经授权执行：计划完直接开工。

**你会得到什么**：`docs/plans/日期--主题-plan.md`（或项目惯用的任务系统里的计划），外加（如需要）恢复面文件。

**怎么配合**：上游是 `brainstorm` 的批准 Spec；下游按需路由——要改代码 `implement`、要深检 `review`、故障原因不明 `diagnose`。

**小贴士**：小任务（一句话能说清、无跨文件依赖）不落计划文件，对话里说清就够——这个技能不会为了仪式感给你制造文档。

> 协议原文：[`skills/plan/SKILL.md`](../skills/plan/SKILL.md)

### implement —— 范围明确地改代码

**解决什么问题**：这是干活主力。范围清楚（有请求/Spec/计划/审查发现兜底）时，它负责把改动做出来、验证过、该提交的提交。核心纪律是：**行为改动先写失败测试再实现**，防止「改完看起来能跑」的假象。

**你会怎么说**：「实现这个计划」「把第 2、3 步做了」「按刚才 review 的发现修一下」。

**它带你走什么流程**：

1. 读相关代码和测试，确认目标行为和保护边界（不碰你未提交的无关改动）。
2. 和你商定**测试缝（seams）**——从外部能看到行为变化的公共接口（API、CLI 输出这类），测试只放在缝上，不对着内部实现细节写。
3. 行为改动走红绿循环：先写一个会失败的测试（红）→ 写刚好让它通过的实现（绿）→ 一次只做一小片。文档和低风险配置不机械套这套。
4. 验证有节奏：类型检查常跑、单文件测试常跑、完整测试收尾跑一次；已经验证过且代码没变的部分不重跑。
5. 长任务不等收尾：有了新证据或关键决策，随时写进本轨道的断点文件。
6. 收尾：低风险改动自审+针对性检查后直接完成，默认落一个 commit；复杂改动（跨模块、权限/数据边界）转 `review` 深检。

**你会得到什么**：改好的代码、跑过的验证证据、一个清楚的改动说明（改了什么、验证了什么、还剩什么）。

**怎么配合**：被 `plan`/`ship`/`review`（修复回环）驱动；干活时**驱动 `tdd`** 纪律；干完按风险去 `review` 或 `cleanup`。

**小贴士**：「必需验收失败或结果未知」时它不会说「完成」——这是整套技能最核心的诚实条款。

> 协议原文：[`skills/implement/SKILL.md`](../skills/implement/SKILL.md)

### diagnose —— 查明「为什么坏」

**解决什么问题**：构建红了、测试挂了、线上报错，但你不知道原因。瞎改一通碰运气是最大的时间黑洞——这个技能用证据把原因钉死再修。

**你会怎么说**：「CI 为什么红了」「这个报错哪来的」「这个接口怎么突然慢了」。

**它带你走什么流程**：

1. **保护现场**：记下完整命令、工作目录、环境、退出码、日志——先拍照再动手术。
2. **能复现才复现**：合理成本内复现一次；昂贵的 GPU 任务、线上环境不会为了「凑次数」反复跑。
3. **提出假设**：复现困难时基于日志和源码提出候选解释，并标明不确定性——不会把猜测说成结论。
4. **对照实验**：给候选原因排序，用最小的检查区分它们；单个实验保持变量可归因，独立的只读检查并行做。
5. **最小修复**：证据充分后在授权范围内修，然后回头验证**原始症状**和受影响路径，不只验证「我改的那行」。
6. **落经验**：值得复用的根因写进项目经验库（lessons），下次同类故障直接翻账本。

**你会得到什么**：故障描述、被证实/排除的假设、根因（或如实的「未定」）、修复及验证证据。只要诊断不要修复也可以——只读诊断直接交付结论。

**怎么配合**：原因查明后转 `implement` 修复；修复复杂或你要求评审时接 `review`。

**小贴士**：已经知道哪坏了的小修补不用它——直接修就行，技能之间切换不为仪式而仪式。

> 协议原文：[`skills/diagnose/SKILL.md`](../skills/diagnose/SKILL.md)

### review —— 审查改动，裁决「到底完成没有」

**解决什么问题**：两个问题一次解决——改动质量有没有问题？宣称的「完成」有没有真凭实据？普通 agent 的「我检查过了」是自我汇报，这个技能只认实际跑出来的输出。

**你会怎么说**：「审一下这次的 diff」「验证一下刚才说的完成」「review 这半个成品」（WIP 也能审，不必等写完）。

**它带你走什么流程**：

1. 明确审哪个版本、目标行为是什么、验收标准是什么。
2. 按具体故障路径查正确性、边界、合同、回归——不是走形式地扫一眼。
3. 有价值且环境允许时，派一个**只读的独立子代理**冷眼复核（「自己写检查自己过」是这套方法明确防范的自欺）。
4. 把每条必需标准映射成 **pass / fail / unknown** 三态。关键规则：口头断言不算证据；相关代码没变的旧验证结果可以复用，不为了「仪式」重跑。
5. 裁决：没有未解决的阻断问题、必需标准全部 pass，才判 ready。Critical/Important 级问题必须解决；unknown 不算通过。

**你会得到什么**：两份清单——「正确性与风险」（每个发现的严重度、位置、触发条件）和「验收证据」（每条标准的三态判定），加上剩余缺口和结论。需要跨会话处理的发现会落盘到 `docs/reviews/`。

**怎么配合**：上游是 `plan`/`implement`/`ship`；发现已授权修复时直接回 `implement` 修，修完只复验受影响部分。`verify` 是它的别名——说 verify 也是进这里，不会跑两轮。

**小贴士**：低风险小改动不用专门开 review，`implement` 自审就够；这个技能自己会做这个判断。

> 协议原文：[`skills/review/SKILL.md`](../skills/review/SKILL.md)

### ship —— 授权任务一条龙干到底

**解决什么问题**：你已经明确授权、范围也清楚的任务，不想一句句盯着「先实现→现在审→最后收尾」地发指令。ship 把这三段串成一次交付。

**你会怎么说**：「这活授权了，从头做到尾」「ship it」。

**它带你走什么流程**：

1. **确认前置**：范围和验收清楚、已授权走完全程——不满足就先转 `brainstorm`/`plan`/`diagnose`，解决后再回来。
2. **implement**：最小修改+测试驱动+针对性检查。
3. **review**（按风险）：实质风险的改动才深检；低风险机械改动自审后直接进收尾——不会为了排场强制走完全套。
4. **cleanup**：收尾整理，恢复面形成下一会话可接续的状态；任务在本轮关闭则走退休流程（见 cleanup 条目）。
5. 交付摘要：改动概览、证据、收尾结果、剩余事项。

**顺序纪律**：后一阶段不无故推翻前一阶段；review 发现问题只重做受影响部分；不跳过收尾提前邀功，也不把收尾扩大成全仓大扫除。

**你会得到什么**：一次完整交付——代码、证据、整理好的状态，中间不需要你再发号施令。

**怎么配合**：它只是编排者，各段协议仍是 `implement`/`review`/`cleanup` 的；不新增任何额外闸门或重复确认。

> 协议原文：[`skills/ship/SKILL.md`](../skills/ship/SKILL.md)

### cleanup —— 干完活把现场收拾干净

**解决什么问题**：任务做完后的「熵」：README 没更新、旧实现没删、临时文件躺着、恢复状态还挂着 active。不收拾，三个月后仓库变成没人敢动的黑洞。

**你会怎么说**：「收尾」「整理一下这次任务的影响面」。

**它带你走什么流程**：

1. 找到本任务的权威入口（恢复面行或本次 diff）。
2. 只整理**本次任务影响**的文档、生成物、恢复记录——不越界搞全仓清理（那是 `sweep` 的活）。
3. 清掉本次引入的代码遗留：死代码、未用导入、被替代的旧实现；删除以引用证据为准，删后跑针对性检查确认行为没变。
4. 任务关闭（完成/放弃/阻塞/交接）时走**退休四步**：任务行翻出 active → 有价值的经验蒸馏进 lessons → 删本轨道的计划/Spec 临时文档（git 历史就是归档）→ 断点文件同步翻转。四步在同一个 commit 里完成。
5. 没有漂移可以零修改结束——收拾干净不等于必须改点什么。

**你会得到什么**：与实际结果一致的任务记录、清爽的恢复面、以及「下一个任务/下一个会话不会踩到本次残留」的保证。

**怎么配合**：被 `ship`/`implement`/`autoresearch` 在收尾阶段调用；你要显式全仓 Python 死代码清理它路由 `remove-deadcode-py`，显式全仓对账路由 `sweep`。

**小贴士**：untracked 的文件（没进 git 的）它一律不删——要么建议补 commit，要么建议补 .gitignore，处置权在你。

> 协议原文：[`skills/cleanup/SKILL.md`](../skills/cleanup/SKILL.md)

### autoresearch —— 交办一个目标，自动「研究-干活-审核-蒸馏」到完成

**解决什么问题**：你有一个要做的活或要查的问题，但方案完全没想好。普通 agent 要么先问你一堆问题，要么闷头做一版就交差。这个 skill 接了活就独立跑：自己调研、自己动手做实验改代码、自己对抗审查自己的结论，对照完成判据检查——没完成就排除掉被证伪的解释继续，直到真完成，或诚实地告诉你卡在哪。

**你会怎么说**：「研究一下：推送该用长轮询还是 WebSocket，查到有结论为止」「这个性能问题查清楚并验证」（会话断了就说「autoresearch \<研究日志路径\>」续跑）。

**它带你走什么流程**：

1. **立项摸底**：把你的话定成一句话目标＋范围边界＋完成判据（什么算完成，全程固定）；扫一遍已知信息和候选解释写进日志。
2. **自动循环**，每轮四段：**研究**（立一个可证伪假设，写进日志）→ **干活**（并行查一手来源；需要动手就直接跑实验、写测量脚本、分支上改代码验证）→ **审核**（对抗视角挑自己结论的刺，连"要不要开下一轮"都要审）→ **蒸馏**（结论与经验落日志）。
3. **完成检查**：对照完成判据——完成 → 终态；没完成 → 过排除法三问（排除了什么？还剩什么没区分？下轮怎么区分？）续轮。
4. **终态交账**：五种诚实终点（answered/inconclusive/blocked/预算尽/取消），结论节**结论先行＋逐条证据链接**，只读这一节就能拿走答案。

**什么时候会来问你（仅四种）**：要花钱、要外部写入、不可逆或影响生产、你主动叫停——查资料、本地实验、分支上改代码验证全部免打扰。想看过程可以说「每轮停下来给我看」。

**你会得到什么**：一份研究日志——最终答案＋每轮假设/证据/裁决全程可追溯；它是持久交付物，断了随时续跑。

**怎么配合**：单发小查证用轻量的 `research` 就够；结论要落地成正式改动接 `plan`/`implement`。

> 协议原文：[`skills/autoresearch/SKILL.md`](../skills/autoresearch/SKILL.md)

### harness-builder —— 给项目搭/修 agent 工作台

**解决什么问题**：一个新项目想让 agent 干活，得先有基本工作台：入口说明（AGENTS.md）、存档系统（恢复面）、验证闸门。或者已有工作台坏了/不够用了。这个技能是工作台的总包工头。

**你会怎么说**：「给这个新项目把工作台搭起来」「修一下这个项目的 harness」「审计一下我的 AGENTS.md 配得怎么样」。

**它带你走什么流程**：

1. 读项目的入口、配置、脚本和实际报错，确认现状和缺口。
2. **只对真实缺口动手**：简单修复直接说清改哪个文件；跨领域改造用一张推荐矩阵汇总（缺口→证据→处理→验证）。审计/推荐请求保持只读。
3. 需要帮手时按缺口路由：改给 agent 读的文字 → `writing-for-agents`；选型 → `capability-recommender`；找现成技能 → `find-skills`。
4. 修改落 canonical 源，同步受影响的安装面文档，验证真实目标。
5. **不默认安装**任何 hooks、MCP、子代理配置——没有缺口就不加东西，零推荐是合法结果。

**你会得到什么**：与缺口相称的工作台配置（或一份只读建议），不多不少。

**怎么配合**：日常任务**不经过它**——单任务的建档由 `plan` 自动做，不用惊动总包工头；只有真缺工作台或工作台坏了才找它。

**小贴士**：第一次在新项目用这套技能时说一句「用 harness-builder 接入」，之后日常干活就不需要它了。

> 协议原文：[`skills/harness-builder/SKILL.md`](../skills/harness-builder/SKILL.md)

## 辅助技能：为车道查缺补漏

### find-skills —— 定向找一个现成技能

**解决什么问题**：你明确缺一个能力（比如「解析 PDF」），想知道有没有现成的第三方技能可用，而不是让 agent 现造轮子。

**你会怎么说**：「找一个能解析 PDF 的现成技能」「找个 skill 干 X」。

**它带你走什么流程**：明确缺口和运行时 → 定向搜索候选 → **逐个安全审计**（读它的 SKILL.md 和会执行的内容，过一遍红旗清单：会不会偷偷写 shell 配置、注册 hooks、外传数据、要求提权？命中即淘汰）→ 只给符合条件的候选及安装范围。

**边界**：搜索不等于安装授权——找到的候选给你过目，装不装、装到哪（项目级/用户级）由你决定。普通「怎么做」问题不会触发它，别担心日常问答被打断。

> 协议原文：[`skills/find-skills/SKILL.md`](../skills/find-skills/SKILL.md)

### capability-recommender —— 只读的能力选型参谋

**解决什么问题**：感觉工作流缺了点什么，但不知道缺的是技能、hooks、MCP 还是子代理。它帮你把缺口翻译成具体的能力选型建议，但**只建议、不动手**。

**你会怎么说**：「我这套工作流还缺什么能力」「该不该给这个项目加 MCP」。

**它带你走什么流程**：先查现有工具够不够（够用就直接说够用，零推荐收工）→ 只调查能补缺口的候选 → 按任务价值、兼容性、权限、维护成本比较 → 输出紧凑推荐（缺口→候选→理由→安装范围→验证），必要时分 Required/Recommended/Deferred/Rejected 四级。

**边界**：推荐等级不是安装授权；下载量和 stars 只作背景不作门槛；第三方候选同样过安全红旗。

> 协议原文：[`skills/capability-recommender/SKILL.md`](../skills/capability-recommender/SKILL.md)

### writing-for-agents —— 修改「给 agent 读的文字」

**解决什么问题**：skills 本身、AGENTS.md/CLAUDE.md 这类持久指令、恢复面文件——这些是 agent 每次运行都会读的「制度文件」。改它们和改代码是两种手艺：要让 agent 每次都走同样的过程，而不是产出同样的结果。

**你会怎么说**：「改一下 XX skill 的这条规则」「帮我审计修订项目的 AGENTS.md」「修复一下 .harness 恢复面」。

**它带你走什么流程**：找到实际生效的文件（全局/项目/子目录分层）→ 对照现状区分过时、冲突、重复、过宽触发和仍有价值的约束 → 完成修订并报告每个改动的位置、后果和理由。改 skill 写作纪律、恢复面选型都有对应参考文档。

**边界**：在目标项目**搭**工作台用 `harness-builder`；这个技能只管**文字与协议**本身的修订。

> 协议原文：[`skills/writing-for-agents/SKILL.md`](../skills/writing-for-agents/SKILL.md)

## 纪律技能：实现时的测试规矩

### tdd —— 先红后绿的测试纪律

**解决什么问题**：agent 写测试最常见的三种自欺：测的是实现细节（一重构测试就红，行为明明没变）、断言用实现自己算的值（同义反复，永远通过）、先写完实现再补测试（测试只是复述）。这条纪律把这些堵死。

**它是什么**：它不独立干活，由 `implement` 在实现行为改动时**驱动**，你也可以显式要求（「这块用 TDD 写」）。规矩四条：

1. **测试只放在缝上**：缝=从外部能看到行为的公共接口。写测试前先写下要测哪些缝并和你确认。
2. **先红后绿**：先写一个会失败的测试，再写刚好让它通过的实现——不多写一行。
3. **一次一片**：一个循环只做一个缝、一个测试、一段最小实现，垂直切着走，不横向铺开。
4. **重构不在循环内**：让测试变绿和整理结构分开做，不混在一轮里越改越乱。

**判断你得到的是好测试的土办法**：测试读起来像一句规约（「用户能用有效购物车结账」），并且实现整个换掉后测试还能活。

> 协议原文：[`skills/tdd/SKILL.md`](../skills/tdd/SKILL.md)

## 工具技能：按需触发的独立工具

四个工具都是**显式触发**的独立入口，不做任务收尾（收尾归 `cleanup`）。

### remove-deadcode-py —— 全仓 Python 死代码清理

**你会怎么说**：「把全仓的 Python 死代码清一清」「删掉没用的代码」。

**它带你走什么流程**：先圈出**不可删区**（入口脚本、CLI 命令、框架自动发现的 models/urls、migrations、conftest）→ Ruff 快通道查未用导入/变量 → vulture 分级扫描（60% 只是线索，90% 可进定罪）→ **三重证据定罪**（全仓 grep 零引用 + git 溯源 + 覆盖率佐证）→ 动态访问守卫清单（`getattr`/注册装饰器/dunder/`__all__` 命中即保留，无论工具怎么说）→ **分批原子删除**（每批删完跑最窄测试，绿了才 commit，红了整批回滚缩小批次）→ 级联重扫（删一批会暴露新一批）。

**为什么信它**：检测靠工具，定罪靠证据，删除分小批——「vulture 报了」从来不是删除理由，证据才是。误报白名单必须写注释说明「它为什么活着」，过期白名单比死代码更危险。

**边界**：只管 Python；JS/TS 用 knip、Go 用 `go tool deadcode`、Rust 用 cargo-machete。大仓不求一次清零，分多次会话，每轮以全绿测试收尾。

> 协议原文：[`skills/remove-deadcode-py/SKILL.md`](../skills/remove-deadcode-py/SKILL.md)

### sweep —— 全仓对账大扫除

**你会怎么说**：「大扫除」「盘点一下仓库」「对个账」。

**它解决什么问题**：日常任务各自收尾，但仓库级别会慢慢沉积——没人引用的计划文档、状态和实际进度对不上的登记、僵尸任务行、untracked 遗留物。sweep 定期把这本账对平。

**它带你走什么流程**：探测恢复面（有哪些状态文件、入口）→ 跑对账清单（状态矛盾？任务产物是否零引用？untracked 有哪些？）→ **六档分类**（任务产物孤儿/僵尸阻塞行/半翻行/untracked 遗留物/归档目录/状态文件超载）→ 机械项自动修，**模糊项列证据交你裁决，不裁决不删**→ 历史任务的收尾残账补走退休四步 → 汇报（已处理/待裁决/保留/下轮候选）。

**为什么信它**：删除要三重证据定罪（零引用+溯源+无交叉引用）；untracked 文件一律不删（出口只有补 commit 或补 .gitignore）；归档目录和 ADR 不动。宁可保守停，不做激进删。

**和 cleanup 的分工**：cleanup 收拾**本次任务**的影响面；sweep 对账**整个仓库**的历史沉积。前者每次任务都走，后者低频按需。

> 协议原文：[`skills/sweep/SKILL.md`](../skills/sweep/SKILL.md)

### research —— 轻量单发调研

**你会怎么说**：「帮我查一下 X」「调研一下这个库的用法」。

**它解决什么问题**：一次性查证——文档/API 的事实、某个主题的摸底、纯跑腿的资料活。不需要 autoresearch 那种多轮假设循环的重量级装备。

**它带你走什么流程**：把需求定成一句可交付的问题 → 派后台代理跑腿（或本会话直接查），**每条结论回溯一手来源**（官方文档、源码、第一方 API），不采信二手转述 → 主会话对过来源才落盘 → 产出一份带逐条出处的 markdown（`docs/research/日期--主题.md`）。

**边界**：单问单答。查着查着发现问题需要多轮验证才能收敛，经你确认后升级转 `autoresearch`；结论要变成代码改动接 `plan`/`implement`。

> 协议原文：[`skills/research/SKILL.md`](../skills/research/SKILL.md)

### handoff —— 会话交接

**你会怎么说**：「交接，下个会话继续」「把手头的活移交给新会话」。

**它解决什么问题**：会话快到头了但活没干完。直接开新会话，新 agent 两眼一抹黑；你手动复述，又漏又累。它把当前会话压缩成一份**零上下文可接手**的交接物。

**它带你走什么流程**：项目有恢复面 → 续点优先写进断点文件（持久、可恢复），关键状态与证据写证据行；没有恢复面 → 交接文档写到系统临时目录（不进仓库，避免制造孤儿文件），把路径告诉你。内容纪律：附「建议技能」一节（下一个 agent 该调哪些技能，直呼其名）；不复述已有产物（引用路径即可）；密钥、口令、个人信息一律不写。

**边界**：交接是显式动作——你不叫，它不自作主张交接。

> 协议原文：[`skills/handoff/SKILL.md`](../skills/handoff/SKILL.md)

## 常见组合速查

| 场景 | 组合 | 说明 |
| --- | --- | --- |
| 一行小修改 | `implement` 自审即完 | 不惊动任何其他技能，验证过就提交 |
| 已授权的明确任务 | `ship`（=implement→review→cleanup） | 一句话授权，一条龙交付 |
| 模糊的新功能 | `brainstorm` → `plan` → `implement` → `review` → `cleanup` | 先聊清方向再动工，全程有据 |
| 命令/构建坏了 | `diagnose` → （授权后）`implement` | 先钉死根因再修，不瞎试 |
| 开放技术问题 | `research`（单发）或 `autoresearch`（多轮） | 小问题轻查，大问题带预算地查到有结论 |
| 新项目接入 | `harness-builder` 一次 → 之后日常用车道 | 工作台搭一次就够 |
| 仓库沉积清理 | `sweep`（全仓对账）+ `remove-deadcode-py`（Python 死代码） | 低频大扫除，证据定罪 |
| 会话要断活没完 | `handoff`（或等 `plan` 建的恢复面自动接续） | 有存档走存档，没存档写交接文档 |

## 第一次上手建议

1. 装完后先试最小的：随便找个小改动说「用 implement 做这个改动」，感受一次「验证过才算完成」的差别。
2. 再试一次完整流：挑一个你愿意授权的小任务说「这活授权了，用 ship 干到底」。
3. 下次开会话前，试着说「plan 一下」，看看任务存档怎么自动建立、断点怎么续。
4. 模糊需求来的时候，让 `brainstorm` 拷问你一次——你会喜欢上「每题带推荐答案」的提问方式。
5. 不必记住全部 17 个：记住「聊清楚（brainstorm）→ 排计划（plan）→ 干活（implement）→ 深检（review）→ 收尾（cleanup）」这条主干，其余的用到再翻本指南。
