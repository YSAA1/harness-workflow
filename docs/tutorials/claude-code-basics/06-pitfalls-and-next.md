# 06 — 常见失败模式 + 下一步

前五节是在建能力，这一节是防倒退。CC 用得不顺手，追溯起来通常就是下面几个模式。

## 模式一：上下文过载——什么都想塞进去

**表现**：CC 越来越慢、答非所问、或者忘了你 10 分钟前说的话。

**原因**：对话历史太长了。你把修 bug、读论文、改配置、分析数据全在一次会话里做，中间没做过 `/clear`。

**正确做法**：话题切换时 `/clear`。如果你想保留一些关键信息（比如"刚才改过哪些文件"），先 `/compact`。

```
一个会话做一类事，而不是一个会话做所有事。
```

**科研场景**：

```
❌ 一个会话里：修数据加载 bug → 调模型结构 → 分析结果 → 画图 → 写论文 related work
✅ Session 1: 修 bug + 调模型 → /compact → 继续调优
   Session 2: /clear → 分析结果 + 画图
   Session 3: /clear → 写论文
```

## 模式二：盲信输出——没让它验证

**表现**：CC 说"改好了"，你信了。实际跑一下——报错。或者更糟，能跑但逻辑不对。

**原因**：你把 CC 当成了"肯定不会出错"，没有给它验证的机会。

**正确做法**：回顾[第三节](03-effective-communication.md)的模式一——每次给任务，附带验证标准。

```
❌ "帮我写一个数据增强函数"
✅ "帮我写一个数据增强函数。写完后跑 python -c 'from src.data.transforms import MixCut; print(MixCut()(torch.randn(3,32,32)))'，确认能正常返回"
```

**CC 不是不会错——但它的强项是能自己发现错、自己修。前提是你给了它验证步骤。**

## 模式三：一次改太多

**表现**：你给了 CC 一个巨大的任务——"重构整个数据加载模块，同时加三个新功能"。它改了一堆文件，你根本审不过来。

**原因**：CC 会在不确定时自己猜。任务越大，猜的链条越长，偏差累积越多。

**正确做法**：增量推进。每次只改一件事，验证通过了再做下一件。

```
❌ "重构数据加载，加 MixCut，改日志格式，统一配置文件"
✅ "先给 transforms.py 加 MixCut 类 → 验证能 import → 再集成到 dataset.py →
   验证能跑 1 epoch → 再改日志格式 → 验证日志输出正确 → …"
```

Claude Code 团队在长任务 agent 研究中验证了这一点：**增量工作 + 每次留下清晰状态，远好于一次做完所有事。**[2]

[2]: 见 Anthropic 工程博客 [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。

## 模式四：没说清楚"不做什么"

**表现**：你让 CC 改 `transforms.py`，它顺手"优化"了 `dataset.py` 里的变量命名。你想保持的代码风格被改了。

**原因**：CC 默认会尝试"帮更多忙"。如果你没画边界，它会自己扩大范围。

**正确做法**：明确说"不要改什么"。

```
在 src/data/transforms.py 里加 MixCut 类。
只改这个文件，不要动其他文件。
不要修改现有的 transform 类。
不要在代码里加新的依赖库。
```

这个习惯也可以在 CLAUDE.md 里固化：

```markdown
## 修改约束
- 每次只改当前任务涉及的文件，不要顺手"优化"其他文件
- 不要改 conda 环境配置
- 不要改 data/raw/ 下的任何文件
```

## 模式五：忘记会话管理，上下文慢性中毒

**表现**：CC 不是突然变差——是一点一点变差的。你不太确定，但总觉得它"没之前聪明了"。

**原因**：上下文里累积了大量中间过程——失败的尝试、废弃的方向、调试输出。这些噪声稀释了关键信息。

**正确做法**：回顾[第五节](05-session-management.md)的决策图。关键习惯：

- 每次完成一个子任务后，问自己"这个话题还需要继续吗？"
- 不需要了 → `/clear`
- 还需要但上下文太长 → `/compact`
- 不确定 → 看 CC 的行为，如果它开始"忘事"或"犯低级错误"，就该 `/compact` 或 `/clear` 了

## 培养直觉：什么时候 CC 会做好，什么时候不会

Claude Code 最佳实践最后一节叫"培养你的直觉"。这不是能教出来的——是用出来的。但有两个经验法则：

**CC 做得好**：
- 任务边界清楚、有明确验证方式
- 项目有良好的 CLAUDE.md
- 有现有模式可以参考（"像 X 那样实现 Y"）
- 每次改动范围小、可独立验证

**CC 容易做不好**：
- 任务定义模糊（"帮我改进代码"）
- 项目结构混乱、没有文档
- 完全从零创造（没有可参考的范例）
- 一次要求改十几个文件
- 上下文已经污染但你没 `/clear`

读完这 6 节，你已经能覆盖科研中 80% 的使用场景。剩下 20%——那些让你从"用工具"到"建系统"的能力——在进阶版中展开：

|-----------|-------------|

| [Skills：可复用科研流程](../claude-code-advanced/02-skills-for-research.md) | 把"搜论文→筛→精读→写笔记"变成一条 `/lit-review` 命令 |

| [对抗验证](../claude-code-advanced/05-adversarial-verify.md) | 让 CC 挑战自己的结论——"为什么这个结果可能是错的？" |

**建议**：先用基础版的技能在日常科研中积累 2-4 周的实际体验。当你开始觉得"这个重复操作每次都要手动说一遍很烦"时，那就是读进阶版的最佳时机。

## 基础版总结

六节内容围绕一条线展开：**认识工具 → 配置项目 → 有效沟通 → 日常实战 → 会话管理 → 避坑前进。**

每个模块都能独立参考，但按顺序读下来，你看到的是同一个项目、同一个人（小李）、同一个科研场景在不同阶段遇到的不同问题。这不是六个知识点——是一套工作方式。

回头看这 6 节最核心的 5 句话：

1. **在项目目录里启动 CC**（01 节）
2. **花 5 分钟写好 CLAUDE.md**（02 节）
3. **每次给任务都给验证标准**（03 节）
4. **先规划再实现，增量推进**（03、04 节）
5. **主动管理上下文——该清就清，该压就压**（05 节）

把这 5 条变成习惯，你就已经超过了 90% 的 CC 用户。
