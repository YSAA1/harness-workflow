# 03 — 有效沟通：给上下文、给验证

CLAUDE.md（上一节）解决了"项目大背景"的问题。但具体到每个任务——让 CC 做什么、怎么做、做完怎么判断对不对——靠的是你每次说话的方式。

这一节拆成四个小模式，每个都能立刻用在科研日常里。

## 模式一：给验证标准，而不只是给任务

这是 Claude Code 最佳实践中放在最前面的建议。对比一下：

| 你这样说 | 你该这样说 |
|---------|-----------|
| "写一个验证电子邮件地址的函数" | "写一个 `validateEmail` 函数。`user@example.com` 应该返回 true，`invalid` 应该返回 false，`user@.com` 应该返回 false。实现后运行这些测试用例" |
| "让仪表板看起来更好" | "[粘贴设计截图] 按这个设计实现。完成后截图对比原设计，列出差异并修复" |
| "构建失败了" | "构建失败，报这个错：[粘贴错误]。修复它并验证构建通过。解决根因，不要抑制报错" |

看出区别了吗？

- **左边**：CC 不知道"怎样算做好了"。
- **右边**：CC 知道自己要做完什么、怎么验证、验证失败后要修正。

科研场景中的例子：

```
❌ "帮我分析一下实验结果"

✅ "读取 experiments/baseline/logs/train.log 和 experiments/augmentation/logs/train.log，
   对比两个实验的 validation accuracy 曲线。用 matplotlib 画双线对比图，
   标注最高 accuracy 点。如果两个实验的日志格式不同，先告诉我差异再处理。"
```

**核心原则**：每次给任务时，附带一个"怎么算做完了"的标准。最简单的标准就是——跑一下，通过就是做完了。

## 模式二：限定范围 + 指向来源

CC 在你的项目里有完整的文件系统访问权限——它能看到的越多，越容易迷失。好的做法是**帮它聚焦**。

| 策略 | 之前 | 之后 |
|------|------|------|
| **限定范围** | "给 foo.py 加测试" | "给 `foo.py` 写测试，覆盖用户已注销的边界情况。不要 mock 数据库" |
| **指向来源** | "为什么 ExecutionFactory 的 API 这么怪？" | "查看 `ExecutionFactory` 的 git 历史，总结它的 API 是怎么演化成现在这样的" |
| **参考现有模式** | "加一个日历组件" | "先看 `HotDogWidget.php` 是怎么实现主页组件的——那是我们的模式。按同样模式实现日历组件，让用户能选月份、翻页。只用项目里已经引入的库" |
| **描述症状** | "修复登录 bug" | "用户反馈会话超时后登录失败。检查 `src/auth/` 里的认证流程，特别是 token 刷新逻辑。写一个能复现问题的测试，然后修复" |

科研场景：

```
❌ "帮我改一下这个模型"

✅ "我想在 src/models/resnet.py 的 BasicBlock 里加一个 channel attention 模块。
   先看 src/models/attention.py 里已有的 SE 模块实现方式，参考它的接口风格。
   改完后跑 python train.py --config configs/baseline.yaml 确认能训练 1 个 epoch 不报错。"
```

### 善用 `@` 引用

CC 支持用 `@` 直接引用文件：

```
看看 @src/models/resnet.py 的结构，然后参考 @src/models/attention.py 的风格，
写一个新的 CBAM attention 模块放到 @src/models/attention.py 里。
```

`@` 引用让 CC 精确知道你在说哪个文件，不需要你自己描述路径。

### 管道输入

你还可以直接把命令输出管道给 CC：

```bash
cat experiments/baseline/logs/train.log | claude "从这个训练日志里提取每个 epoch 的 loss 和 accuracy，画收敛曲线"
```

或者把报错管道进去：

```bash
python train.py 2>&1 | claude "这个报错是什么原因？修复后重新运行验证"
```

## 模式三：先探索，再规划，再编码

科研中常有这种场景：你想给一个开源代码库加新功能，或者在一个不熟悉的数据集上跑实验。这时**不要上来就让 CC 改代码**。

Claude Code 最佳实践建议四步走：

```
探索 → 规划 → 实现 → 提交
```

### 科研场景演示

**探索**：

```
先读一下 src/data/ 目录，了解数据加载是怎么组织的。再看看 train.py 是怎么调用数据加载的。
告诉我数据 pipeline 的整体流程。
```

**规划**：

```
我想加对 CIFAR-100 数据集的支持。基于你刚才了解的现有数据 pipeline，
哪些文件需要改？具体怎么改？给我一个计划，先别写代码。
```

（也可以用 `Ctrl+G` 触发生成式规划。）

**实现**：

```
按你的计划实现。写完后跑 python train.py --config configs/cifar100.yaml
确认能训练 1 个 epoch 不报错。有任何报错自己修。
```

**提交**：

```
提交这些改动，commit 信息写清楚加了什么、改了哪些文件。
```

**这四步的价值不在每一步本身，而在于"先想清楚再动手"**。CC 在没有方向的时候会自己猜着改，猜错了你还要花时间回退。花 30 秒让它先探索和规划，省的是后面 10 分钟的修正。

## 模式四：让 CC 采访你

如果你有一个模糊的想法，但自己也说不清楚具体怎么做——这正是科研中最常见的情况——可以让 CC 反过来问你：

```
我想做一个小实验，对比三种数据增强策略对分类精度的影响。
用 AskUserQuestion 工具详细采访我——问清楚数据集、模型、评估指标、
实验设计、边界条件、我可能没考虑到的陷阱。采访完把所有内容总结到 experiments/augmentation-study/PLAN.md。
```

CC 会像导师一样追问：你的 baseline 是什么？怎么保证对比公平？随机种子固定了吗？每个策略跑几次取平均？

**用这个模式的前提**：你自己对问题有基本理解，但需要有人帮你结构化。如果自己完全没想法，CC 问的问题你也答不上来。

## 本节要点

四个模式，按使用频率排序：

1. **给验证标准**：每次任务附带"怎么算做完了"——跑一下能通过就是做完了。
2. **限定范围 + 指向来源**：用 `@` 引用文件，用 git 历史追溯，用现有代码当范例。
3. **先探索再规划再编码**：30 秒的规划节省 10 分钟的修正。
4. **让 CC 采访你**：模糊想法 → 结构化追问 → 清晰计划。
