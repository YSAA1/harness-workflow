# Scoped implementation

用户请求、项目规格或计划可直接提供执行范围。无需为常规修改补齐全部流程工件。

## 流程

1. 阅读相关入口、源码、测试和 git 差异，确定目标行为与必要验证；保护无关用户改动。
2. 完成最小相关修改。修 bug 优先复现，适合时增加真正覆盖故障的回归测试；文档、低风险配置不机械要求先写失败测试。
3. 运行覆盖实际影响面的检查。新改动影响已验证路径时重跑对应检查；已完成且仍适用的证据可复用，不因换技能重跑。
4. 更新受影响的用户文档和已有恢复记录；没有变化的文档无需修改，不新建重复状态文件。长任务不等收尾：新证据、被排除的假设或关键决策出现时即写入已有恢复面；持续探索后按需重读当前 plan/任务入口，防目标漂移。
5. 按下述完成条件收尾，或继续已授权的后续步骤。只在实质扩大范围、改变验收或遇到授权边界时询问。

## 完成条件

- 低风险、范围清楚的修改可在自审和相关检查后直接完成、按项目要求提交；不限于单行修改。
- 复杂行为、多模块合同、权限/数据边界，或用户要求 review 时，使用 `review` 进行更深入评审。`verify` 只是同一入口的别名，不串行追加一轮。
- 必需验收失败或 unknown 时，不宣称对应能力 ready；可以完成独立部分，并具体报告剩余缺口。
- 根因未知且需要调查时用 `diagnose`；明确的局部错误可直接修复，不为了切换技能而停顿。
- 验证强度的参考见 `references/verification-intensity.md`。

## 输出

说明改动、验证、尚存问题及是否提交。需要追踪时记录证据所对应的工作树/配置/输入；简单任务不强制填空表。

## Recommended next skill

- 简单任务已验证：结束或继续用户已授权的下一步。
- 需要深入检查：`review`；未知故障：`diagnose`。
- 本次影响文档或恢复状态需整理：`cleanup`；实质范围变化需要重排依赖：`plan`。
