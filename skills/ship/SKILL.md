# 一次交付：$implement -> $review -> $cleanup

把已授权任务在一次会话内走完修改、评审和收尾。本 skill 只负责编排顺序与中止条件，各阶段协议以对应 skill 为准。

## 流程

1. 确认前置条件：范围和验收已清楚、任务已授权走完全程。范围不清转 $brainstorm/$plan；失败根因未知转 $diagnose，解决后再回来继续。
2. 执行 $implement：最小修改 + 商定 seams 测试驱动 + 针对性检查。低风险机械改动按其完成契约自审后即可进入收尾。
3. 实质风险修改（跨模块、权限/数据边界、部署、用户明确要求）继续 $review：结构审查 + fresh evidence 判定；Critical/Important 发现回到修改并复验受影响部分。
4. 执行 $cleanup：文档、代码与遗留物整理，恢复面形成下一会话可接续的状态。任务在本轮关闭时含退休契约：本轨道行翻出 active 的同一 commit 内走完翻行 → lessons 继承 → 删本轨道文档（含未批准/放弃件）→ state 同步。
5. 输出交付摘要：改动概览、证据与结论、收尾结果、剩余事项。

## 并行模式

触发：计划含依赖边且同时可开工的项 ≥2，并且宿主支持后台子代理与 git worktree；否则走上面的串行流程。本节只替换第 2–3 步的执行方式，前置条件、cleanup 与顺序纪律不变；与串行不同，并行模式总跑一次 review（多个子代理产出的合并结果不适用低风险自审豁免）。

1. 建唯一**集成分支**。可选先派一个探索子代理，把代码/文档调研笔记写到仓库外的公共目录，供后续实现子代理共用。
2. **frontier**＝依赖已全部**合入集成分支**的项——按集成分支实况计算，不看 tracker 的阻塞计数（它要等前置关闭才下降，运行中是过期的）。frontier 上每项派一个后台实现子代理，各用独立 worktree 与分支。
3. 派发靠**上下文指针**（计划路径、项编号、探索笔记路径、相关 commit），不贴摘要。派发词显式要求按 `implement` 执行、行为改动按 `tdd` 先红后绿——子代理不会自动继承本会话加载的纪律。
4. 每个实现子代理：开工、任何编辑之前先确认 worktree 基于集成分支（否则重置到它上面）；交付前把集成分支最新提交合进自己的分支，使落地是 fast-forward。总控合入后重算 frontier，立刻派新的可开工项。
5. 验证依赖未跟踪文件（gitignore 的 fixture、本地数据库、凭据）的项在主工作区（检出集成分支）跑：worktree 只含 git 跟踪的内容，测试在那里静默跳过不算绿。
6. **全部项合入后只跑一次 `review`**（中途 review 会把尚未建的项判为缺失，触发修-审循环）。发现交一个修复子代理统一修，之后只对修过的点做针对性复验，不再开第二轮全面审查。
7. **恢复面只由总控写**：子代理只交 commit 与简报，不碰 `.harness/` 等状态文件；review 修复完成后集成分支 fast-forward 合入主分支，总控回到主分支上照常走 cleanup（退休契约「已 commit 进主树」以主分支为准），最后清理全部 worktree。

适用边界：本模式适合在会话内可观察、可干预的并行；真正无人值守的批量执行，用确定性脚本或 CI 循环更快、更省、更可靠。

## 顺序纪律

- 后一阶段不无故推翻前一阶段；review 发现需改时，只重做受影响部分。
- 不跳过 cleanup 提前收工，也不把 cleanup 扩大成全仓整理。
- 任何阶段遇到授权边界或需要用户决策的取舍：停下说明，不代用户决定。

## Recommended next skill

- 交付完成：结束。
- 未决发现或被阻塞：按对应 lane 记录并交接。
