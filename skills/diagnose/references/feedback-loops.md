# 反馈回路构造菜单

> 用于 `diagnose` 第 2 步。思路改编自 [mattpocock/skills](https://github.com/mattpocock/skills) `diagnosing-bugs`（MIT），revision `b0618bc`（2026-10-08）。

建对回路，故障就修好了九成。大致按此顺序尝试：

1. **失败测试**：在能触及故障的任一 seam 上（单元、集成、e2e）。
2. **curl / HTTP 脚本**：对运行中的开发服务器发请求。
3. **CLI 调用 + 快照 diff**：固定输入，stdout 与已知正确快照比对。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，断言 DOM、console、网络。
5. **回放捕获的 trace**：把真实请求/负载/事件日志存盘，单独回放经过故障代码路径。
6. **一次性 harness**：起系统的最小子集（一个服务、依赖 mock 掉），一次函数调用即走到故障路径。
7. **property / fuzz 循环**：故障是「有时输出错」时，跑上千组随机输入找失败形态。
8. **二分 harness**：故障出现在两个已知状态（commit、数据集、版本）之间时，把「启动到状态 X → 检查」自动化，用 `git bisect run`。
9. **差分回路**：同一输入分别跑旧版/新版（或两套配置），diff 输出。
10. **人在回路脚本（最后手段）**：必须有人点击时，用脚本逐步提示人操作并收集输出，让回路仍是结构化的、输出回流给 agent。

## 收紧回路

- 更快：缓存初始化、跳过无关启动、收窄测试范围。
- 信号更尖：断言具体症状，而不是「没崩」。
- 更确定：固定时间、固定随机种子、隔离文件系统、冻结网络。

30 秒且偶发的回路只比没有好一点；2 秒且确定的回路是排障利器。

## 偶发故障

目标不是干净复现，而是**更高复现率**：循环触发 100 次、并行、加压、收窄时间窗、注入 sleep。50% 复现率可调试，1% 不可——持续提高复现率直到可调试。
