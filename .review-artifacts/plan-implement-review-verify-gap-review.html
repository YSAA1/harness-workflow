总判断：你的四段路线已经避开了很多热门框架的重入口问题：不强绑三文件、保留轻路径、以 fresh evidence 为 ready 前提、把 harness-builder 从强前置改成 gap-driven 工作面修复。现在最该补的是把这些原则从“文本纪律”推进到“机器可校验的 gate 和结构化证据”。

最高优先级缺口

Criticalverify 还不是唯一 ready gate

review 的 recommended route 允许“Pass and evidence is already fresh -> cleanup”，但 README 和 verify 又把 ready claim 归给 verify。这会让 agent 用结构审查替代最终验证。

建议：把 review pass 后统一路由到 verify；证据已新鲜时只允许 verify fast-path，不能直接 ready。

Criticalfresh evidence 缺少 claim 级结构化记录

当前主要靠自由文本记录 freshness、commands、covered behavior、unknowns。对多文件、多阶段、UI/E2E 任务，伪验证仍然容易混进来。

建议：verify 输出最小 schema：claim_id、covered_paths、latest_change_ref、commands、skipped_high_value_checks、unknowns。

Majorplan 输出 schema 和路由不一致

plan 推荐“release-readiness check -> verify”，但正式输出格式只允许 implement | diagnose | harness-builder。

建议：把 verify 纳入 plan 输出 schema，同时把 verification_path_status: runnable | blocked 前移到计划阶段。

Major大任务缺少最终集成 claim

WIP=1 能防止局部漂移，但多 slice 任务仍可能每段局部通过、整体未证明。

建议：plan 增加 final_integration_claim；verify 在多阶段或多 commit unit 时必须验证它。

外部趋势

spec as living artifact issue tracker as control plane isolated workspace trace / trajectory trust layer status / cancel / result structured gates

热门文章和 repo 的共识不是“写更多 prompt”，而是把状态、执行、验证和恢复做成可观察、可回放、可阻断的系统。

你的仓库语义比很多框架干净，但缺少它们已有的一些工程外壳：状态命令、任务隔离、trace、可取消长任务、CI/action 级 review gate。

和热门实践的对照

对标来源它强调什么你的现状应该补什么
OpenAI Harness Engineering 设计环境、指定意图、反馈循环，让 agent 可靠工作。 方法契约和 skill 边界已经对齐。 把 review/verify loop 做成更硬的 gate。
GitHub Spec Kit spec -> plan -> tasks -> implement，每阶段验证后再前进。 已有 brainstorm/plan/implement，但 tasks 层较轻。 给 single-slice 和 multi-slice 分别定义 task contract。
Anthropic Context Engineering just-in-time context、compaction、轻量索引，避免 context rot。 要求读取 recovery surface，但缺少 context budget。 定义 hot context index 和“只读最近证据”的恢复规则。
GitHub Trust Layer 不要让 agent 自评；验证 essential states，而不是僵硬脚本。 verify 有 evidence ladder，但结构化不足。 为 UI/E2E/非确定任务加入 essential outcome schema。
Archon / Rigg / goat-flow YAML workflow、audit、status dashboard、pass/fail checks。 你的流程更轻、更可解释。 补最小 audit/check，不照搬厚工作流引擎。
SWE-agent / AgentLens / Auto-harness 轨迹、失败挖掘、过程级评分、回归 gate。 Research Route 有 evidence loop，但日常四段路线较少 trace。 给 review/verify 增加 provenance 和 outcome ledger。

不建议照搬

  • 不要学 SuperClaude 式大量 slash command 和人设入口；它会冲淡你现在的薄入口优势。
  • 不要把 Archon/Rigg 的 YAML DAG 原样搬进来；你的仓库定位是 workflow skills，不是另一个 workflow runner。
  • 不要默认开启厚 review gate；小任务会被 token 和上下文成本拖慢。
  • 不要把 planning、knowledge、task state 拆到过多 surface；真相源会重新变得混乱。

建议改造顺序

1
收紧 ready gate。所有 meaningful change 通过 review 后必须进入 verify；小任务仍可 implement -> verify。
2
结构化 verification record。先加最小 claim schema，不急着做数据库或 runner。
3
计划阶段前移验证可运行性。新增 verification_path_status，blocked 就回 harness-builder。
4
给多 slice 加 final integration claim。避免局部通过、整体未证。
5
补轻量状态/审计命令。类似 status/result/cancel 的思想可以借鉴，但应保持 repo-local、低耦合。
